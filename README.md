# agent-28days

一名测试工程师用 28 天转型 Agent 工程师的学习记录与项目代码。

本仓库的第一个完整项目是 **缺陷报告生成器**：输入一段口语化的 bug 描述，自动整理成结构化的缺陷报告（JSON + Markdown），支持单条和批量处理。全部基于本地模型运行，不需要 API Key。

## 缺陷报告生成器

### 它能做什么

输入：

```
点击登录按钮后页面一直转圈，等了一分钟也没反应，换浏览器也一样
```

输出（Markdown 版本，同时保存一份 JSON）：

```markdown
# 点击登录按钮后页面持续加载无响应

| 字段 | 内容 |
|---|---|
| 所属模块 | 登录 |
| 严重程度 | S1（致命） |
| 环境 | 未提供 |

## 复现步骤

1. 打开登录页面
2. 输入账号和密码
3. 点击登录按钮

## 预期结果

登录成功并跳转到首页

## 实际结果

页面一直显示加载中，超过一分钟无响应
```

### 快速开始

**1. 准备环境**

需要 Python 3.10 及以上版本，以及 [Ollama](https://ollama.com)（用于在本机运行大模型）。

```bash
git clone https://github.com/2300503017-lwn/agent-28days.git
cd agent-28days
python -m pip install -r requirements.txt
```

**2. 不装模型，先用 Mock 模式试跑**

```bash
python day6_bugreport.py "点击登录按钮后页面一直转圈" --mock
```

Mock 模式用假数据代替模型，可以在几秒内验证整个流程是否正常，包括"第一次输出不合格 → 自动重试 → 成功"的过程。

**3. 下载模型，正式运行**

```bash
ollama pull qwen2.5:3b
python day6_bugreport.py "点击登录按钮后页面一直转圈"
```

生成的报告保存在 `reports/` 文件夹中。

### 用法

| 命令 | 说明 |
|---|---|
| `python bug_report.py "描述"` | 直接传入一条描述 |
| `python bug_report.py -f bug.txt` | 从文本文件读取一条描述 |
| `python batch_report.py -b bugs_sample.txt` | 批量模式：文件中每行一条描述，生成汇总报告 |
| `python bug_report.py` | 不带参数，进入交互输入 |
| `--mock` | 不调用模型，用假数据测试流程 |
| `-m 模型名` | 指定 Ollama 模型，默认 `qwen2.5:3b` |
| `-o 文件夹` | 指定输出位置，默认 `reports` |

批量模式会在 `reports/batch_时间戳/` 下生成每条描述的报告，以及一份 `summary.md`，统计成功率、首次通过率和耗时。

### 实现要点

整个流程是：**描述 → 调用模型 → 清洗输出 → 校验 → （失败则带着错误信息重试）→ 保存**。几个关键设计：

- **用 pydantic 定义报告结构**：字段类型、取值范围（严重程度只能是 1～4）、标题长度等规则都写在 `BugReport` 类里，模型输出不符合就会被拦下。
- **强制 JSON 输出**：请求中通过 Ollama 的 `format` 参数传入由 pydantic 自动生成的 JSON Schema，从生成阶段就约束输出结构。
- **带反馈的重试**：校验失败时，把模型的错误输出和具体错误信息一起发回给模型，让它对照修改，最多重试 3 次。
- **降低随机性**：`temperature` 设为 0，让同一描述的输出尽量稳定。
- **抑制幻觉**：system prompt 明确要求"不编造描述中没有的信息，缺失的字段填写未提供"。
- **可测试性**：模型调用函数可以被替换，`--mock` 模式即基于此实现，可以在不依赖真实模型的情况下测试重试、失败处理等逻辑。

## 学习记录

| 天数 | 主题 | 相关文件 |
|---|---|---|
| 第 1 天 | 搭建环境，跑通第一次模型调用 | — |
| 第 2 天 | async/await、httpx、pydantic 基础 | `day2_*.py` |
| 第 3 天 | 多轮对话原理、system prompt 对比 | `day3_*.py`、`day3_notes.md` |
| 第 4 天 | 结构化输出、JSON 校验、自动重试 | `day4_*.py`、`day4_note.md` |
| 第 5 天 | token、上下文窗口、temperature、幻觉；稳定性测试 | `day5_*.py`、`day5_notes.md` |
| 第 6 天 | 项目：缺陷报告生成器（单条 + 批量） | `bug_report.py`、`batch_report.py`、` bugs_sample.txt` |
| 第 7 天 | 复盘与文档 | `README.md` |

一些阶段性收获：

- 大模型本身没有记忆，多轮对话的"记忆"来自程序每次重新发送的完整聊天记录，因此对话越长 token 消耗越大。
- 大模型的输出天然存在波动，不能像传统测试那样用精确匹配做断言，需要校验格式、关键信息，并通过多次运行统计成功率。
- 仅靠 prompt 约束 JSON 格式并不可靠，结合强制格式、输出清洗和带反馈的重试，成功率会明显提升。
